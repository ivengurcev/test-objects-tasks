# Мини-CRM «Объекты и задачи»

Мини-CRM для строительной компании: постановщики ведут объекты и назначают задачи, исполнители выполняют назначенные задачи, а постановщики принимают работу или возвращают её на доработку.

**Демонстрация:** [http://2.27.120.66:3003/](http://2.27.120.66:3003/) — контейнер опубликован напрямую на внешнем порту `3003`; Nginx внутри контейнера слушает порт `8080`.

## Возможности и роли

- **Постановщик:** видит все активные объекты и задачи; создаёт, редактирует и логически удаляет объекты и задачи; назначает исполнителей; принимает задачи на проверке или возвращает их с комментарием.
- **Исполнитель:** видит только назначенные ему активные задачи и связанные доступные объекты; берёт задачу в работу и отправляет на проверку; не может просматривать задачи других исполнителей.
- Страница задачи показывает автора, исполнителя, ссылку на объект, статус и описание; история переходов открывается в модальном окне.

Доступ к данным и допустимость операций обеспечивает PostgreSQL через RLS и существующие RPC. В браузере используется только Supabase publishable key; `service_role`, пароли и другие секреты не используются.

## Технологии и конфигурация

React, TypeScript, esbuild, CSS Modules, Yarn `4.18.1` с `nodeLinker: pnpm`, Supabase Auth и PostgreSQL.

Миграции применены в Supabase Cloud; список локальных и облачных миграций сверён командой `yarn supabase migration list --linked`. В Cloud находятся четыре тестовых объекта — это принятый демонстрационный набор.

## Локальный запуск

Нужны Node.js 24+ и Docker для локальной базы.

```sh
corepack enable
yarn install --immutable
```

Создай `.env.local` по примеру `.env.example`:

```dotenv
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_PUBLISHABLE_KEY=your-publishable-key
```

Запусти приложение:

```sh
yarn dev
```

Сервер разработки доступен на `http://127.0.0.1:3000`. Пользователей и профили создаёт администратор Supabase; открытой регистрации в приложении нет.

## Интерфейс и навигация

После входа постановщик открывает `/objects`, исполнитель — `/my-tasks`. Сохранённый URL предыдущей роли больше не выбирает чужой интерфейс; после успешного выхода профиль и URL сбрасываются. Существовавший `MyTasksPage` сохранён и обновлён на общих компонентах.

«Мои задачи» показывает назначенные активные задачи и количество связанных объектов, группирует строки по объектам и использует `DataTable`/`TaskStatusBadge`. Названия объектов не являются ссылками. Принятые задачи скрыты за кнопкой «Принятые задачи (N)» и остаются доступны даже без активных. Возврат из общей карточки задачи исполнителя ведёт на `/my-tasks`.

Список объектов показывает таблицу на широком экране и карточки при ширине до 760 px. Счётчики используют существующие доступные через RLS задачи: «На проверке» — `in_review`, «Выполнено» — `accepted`, «Открыто» — все непринятые задачи, включая находящиеся на проверке. Общая шапка закреплена при прокрутке и вынесена за область анимации. До 640 px она показывает название и аватар с инициалами; полное имя, роль и выход доступны в меню, закрывающемся по клику снаружи и Escape; страница задачи использует ту же одноколоночную компоновку.

Просмотр объекта показывает название, адрес и действия постановщика без внешней карточки. Ниже — количество задач, кнопка создания и таблица; до 760 px задачи отображаются карточками. Каждая строка целиком является ссылкой: работают Enter, Ctrl-клик и средняя кнопка мыши.

Оба списка используют общий `DataTable`, одинаковые кнопки создания — `Button`, статусы — `TaskStatusBadge`. В пустом списке задач отображается общий `EmptyState` с иконкой, заголовком, описанием и единственной кнопкой создания для постановщика. Ссылка «К списку объектов» содержит SVG-стрелку.

Создание и редактирование объекта используют `ObjectForm`, задачи — `TaskForm`. Общие `FormPage`, `FormField`, контролы и `FormActions` обеспечивают единый вид: SVG-ссылка возврата, заголовок и одна белая область шириной до 760 px слева. Валидация, API и маршруты сохранены; несохранённые данные после обновления теряются.

На странице задачи кнопка «История статусов» открывает историю в хронологическом порядке: от создания задачи к последнему событию. «Отправить на доработку» открывает общее модальное окно с обязательным комментарием; при ошибке введённый текст сохраняется. Кнопки изменения статуса находятся в `TaskActions`: после короткого описания — в потоке, при длинном — закреплены у нижнего края с учётом мобильной safe area. Конец описания остаётся доступен при прокрутке. Действия и комментарий по-прежнему проверяет существующая SQL RPC.

Маршруты без перезагрузки страницы:

- `/objects` — активные объекты постановщика.
- `/objects/:objectId` — объект.
- `/objects/:objectId/tasks/:taskId` — задача объекта.
- `/my-tasks` и `/my-tasks/:taskId` — список и задача исполнителя.

Корень `/` открывает домашний экран роли. Прямые ссылки восстанавливаются после входа и обновления страницы; права по-прежнему проверяет Supabase. Формы открываются внутри текущего URL, несохранённые данные после обновления теряются. Сервер разработки и Nginx возвращают `index.html` для вложенных маршрутов. Переходы содержимого занимают 240 мс через View Transitions API; без его поддержки и при `prefers-reduced-motion` экраны переключаются сразу.

Для ручной проверки после `yarn dev`:

1. Войти постановщиком; проверить таблицу при ширине 1440 px и карточки при 390 и 320 px, счётчики и кнопку создания.
2. Открыть объект и задачу, пройти назад и вперёд кнопками браузера и вернуться кнопками интерфейса.
3. Обновить страницу объекта и задачи, скопировать URL в новую вкладку; проверить сохранение сессии и соответствие экрана URL.
4. Проверить создание, редактирование и отмену форм на тестовых данных; войти исполнителем и повторить переходы из «Моих задач».
5. Включить reduced motion в настройках браузера; проверить мгновенное переключение экранов.

Автоматическая браузерная проверка на тестовых ответах Supabase покрыла ширины 320/390/760/1024/1440 px, счётчики, переходы и историю, обновление вложенного URL с сессией, обе роли, создание/редактирование/удаление объекта и отмену форм задач. Она не выполняла записи в Cloud.

- `yarn typecheck` — успешно.
- `yarn build` — успешно.
- Frontend-тесты — **13 пройдено**.
- Локальные pgTAP-тесты — **68/68**.
- `yarn supabase db lint --local` — ошибок схемы нет.
- Cloud Auth/API — read-only проверки с обычными Auth-сессиями постановщика и двух исполнителей прошли; проверены роли, видимость объектов и задач, история, связанные профили и недоступность чужих задач.

Cloud-проверки не изменяют данные. Запрещённые записи и переходы проверялись локально; прямые Cloud-запросы записи для этого не выполнялись.

Запуск frontend-тестов:

```sh
node --test src/app/*.test.mjs src/features/tasks/*.test.mjs
```

Дополнительная прямая проверка API исполнителей (требует запущенного локального Supabase):

```sh
node scripts/check-local-executor-api.mjs
```

Скрипт проверяет три учётные записи двух ролей, изоляцию задач без клиентского фильтра исполнителя, запрет чужих изменений и переходов, неизменяемость истории и полный разрешённый цикл. Он создаёт и удаляет только собственные локальные фикстуры. Локальный email-провайдер отключён, поэтому тестовые запросы используют локально подписанные JWT с ролью `authenticated` и ID созданных Auth-пользователей; настройки Auth не меняются. Привилегированный клиент используется только для подготовки и очистки данных. Вход реальных Cloud-пользователей и RLS чтения отдельно проверены существующим read-only скриптом и в браузере под постановщиком и двумя исполнителями; облачные записи для тестов не выполняются.

Команды для локальной базы и тестов:

```sh
yarn db:start
yarn db:reset
yarn db:test
yarn supabase db lint --local
yarn db:stop
```

`yarn db:reset` пересоздаёт только локальную базу.

## Docker

Образ собирается в два этапа: Node.js 24 и Yarn 4 устанавливают зависимости, запускают typecheck и production-сборку; Nginx Alpine раздаёт `dist/` на внутреннем порту `8080` с SPA fallback. Build arguments `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY` обязательны. Env-файлы исключены из Docker build context.

Собери образ из настроек в `.env.local`:

```sh
set -a
. ./.env.local
set +a
docker build \
  --build-arg SUPABASE_URL \
  --build-arg SUPABASE_PUBLISHABLE_KEY \
  --tag test-objects-tasks:latest \
  .
```

Экспортируй образ и передай его на сервер:

```sh
docker save --output test-objects-tasks.tar test-objects-tasks:latest
scp test-objects-tasks.tar <user>@<server>:/tmp/
```

На VPS загрузи образ и запусти контейнер с прямой публикацией на внешнем порту `3003`:

```sh
docker load --input /tmp/test-objects-tasks.tar
docker run -d \
  --name mini-crm \
  --restart unless-stopped \
  -p 3003:8080 \
  test-objects-tasks:latest
```

Docker направляет внешний порт `3003` прямо на Nginx внутри контейнера, работающий на порту `8080`. Дополнительный Nginx-прокси и HTTPS-терминация не используются.

Проверка главной страницы, статических файлов и SPA fallback:

```sh
curl --fail --head http://2.27.120.66:3003/
curl --fail --head http://2.27.120.66:3003/main.js
curl --fail --head http://2.27.120.66:3003/main.css
curl --fail --head http://2.27.120.66:3003/example/client/path
```

Для обновления образа загрузи его новой версией и пересоздай контейнер:

```sh
docker stop mini-crm
docker rm mini-crm
docker run -d \
  --name mini-crm \
  --restart unless-stopped \
  -p 3003:8080 \
  test-objects-tasks:latest
```

Логи контейнера:

```sh
docker logs --follow --tail 100 mini-crm
```

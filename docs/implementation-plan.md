# План реализации мини-CRM

План следует требованиям [`requirements.md`](requirements.md), ограничениям [`arch-rules.md`](arch-rules.md) и архитектуре [`architecture.md`](architecture.md). Он описывает последовательность оставшейся работы; бизнес-правила из требований не расширяются.

Обновляй статус этапа на `[x]` только после выполнения всех его задач и проверок. После завершения этапа обнови этот документ и связанные разделы README, если фактическая реализация изменила описание проекта. Работай только над текущим незавершённым этапом; к следующему переходи по отдельному указанию пользователя.

**Цель:** подготовить и проверить базу данных, контроль доступа и авторизацию, на которых строятся следующие этапы.

**Задачи:** перечисленные выше подготовительные работы и вход в приложение для обеих ролей. Существующие RLS-политики и RPC повторно не реализовывать.

**Критерии готовности:** база данных, миграции, RLS, RPC и SQL-тесты готовы; тестовые учётные записи настроены; приложение получает роль пользователя и корректно восстанавливает и завершает сессию; обе роли могут войти.

**Проверки:** SQL-тесты; вход менеджера и исполнителя; перезагрузка страницы с активной сессией; выход.

## Этап 1. Объекты

- [ ] Реализовать список активных объектов.
- [ ] Реализовать создание и редактирование объекта менеджером.
- [ ] Реализовать карточку объекта.
- [ ] Реализовать логическое удаление объекта с учётом существующей модели БД.
- [ ] Подключить данные через Supabase SDK и убедиться, что видимость объектов исполнителю ограничивается существующими RLS-политиками.

**Цель:** дать менеджеру возможность вести объекты и обеспечить пользователям предусмотренную требованиями видимость.

**Критерии готовности:** менеджер видит список, может создавать, редактировать и логически удалять объекты, а также открывать карточку; исполнитель видит только доступные ему объекты; удалённый объект не показывается как активный.

**Проверки:** сценарии списка, создания, редактирования, карточки и удаления под менеджером; проверка видимости и запрета доступа под исполнителем; сверка прямыми запросами к Supabase API, что RLS применяется.

## Этап 2. Задачи

- [ ] Показывать список задач выбранного объекта и их статусы.
- [ ] Реализовать создание задачи менеджером через существующую RPC-функцию.
- [ ] Реализовать выбор и назначение исполнителя.
- [ ] Реализовать редактирование только разрешённых полей согласно существующим грантам и требованиям.
- [ ] Реализовать логическое удаление задачи.
- [ ] Отображать статусы в списке задач.

**Цель:** обеспечить ведение задач в контексте объекта, используя готовые операции базы данных.

**Критерии готовности:** менеджер видит задачи объекта, создаёт задачу через существующую RPC с начальным событием истории, назначает исполнителя, редактирует только разрешённые поля и логически удаляет задачу; активные задачи отображаются со статусом. Новые RPC и RLS не создавать, если текущая схема уже обеспечивает нужные операции.

**Проверки:** сценарии списка, создания, назначения, редактирования и логического удаления под менеджером; убедиться, что прямое изменение статуса недоступно и физическое удаление не используется; проверить доступ исполнителей по назначению.

## Этап 3. Карточка задачи и управление статусами

- [ ] Показывать информацию о задаче.
- [ ] Показывать только действия, доступные текущей роли при текущем статусе.
- [ ] Выполнять смену статуса через существующую `transition_task_status`.
- [ ] Требовать комментарий при возврате задачи на доработку.
- [ ] Показывать историю переходов.

**Цель:** предоставить предусмотренные требованиями действия по задаче и просматриваемую историю её статусов.

**Критерии готовности:** карточка показывает данные и историю; интерфейс предлагает только допустимые действия; переходы вызывают существующую RPC; возврат на доработку не отправляется без комментария; база остаётся источником проверки полномочий и переходов.

**Проверки:** сценарии каждого разрешённого перехода для соответствующей роли; попытки недопустимых переходов и переходов постороннего исполнителя отклоняются БД; проверить комментарий возврата и соответствующие записи истории.

## Этап 4. Мои задачи

- [ ] Реализовать список задач текущего исполнителя.
- [ ] Добавить переход из списка в карточку задачи.
- [ ] Отображать связанный объект и статус.
- [ ] Показывать доступные исполнителю действия.

**Цель:** дать исполнителю рабочий список назначенных ему задач.

**Критерии готовности:** исполнитель видит только назначенные ему активные задачи, может открыть карточку, видит объект и статус и выполняет доступные ему действия; ограничения не зависят только от клиентского фильтра.

**Проверки:** проверить список под обоими тестовыми исполнителями, переход в карточку и доступные действия; проверить прямыми API-запросами, что задачи другого исполнителя недоступны.

**Критерии готовности:** демонстрационные данные покрывают основные статусы и обе роли; полный путь менеджера и исполнителя работает; база подтверждает ограничения доступа, RPC и сохранение истории при логическом удалении.

**Проверки:** пройти сквозные сценарии обеих ролей; выполнить прямые API-проверки RLS; проверить вызовы RPC, историю статусов, удаление объекта вместе с его активными задачами и логическое удаление отдельной задачи.

# Предлагаемая архитектура

Документ описывает архитектуру приложения и ограничения его реализации.

## Общая схема

```text
Пользователь
    │
    ▼
React + TypeScript (браузер)
    │ Supabase JavaScript SDK, пользовательский JWT
    ▼
Supabase Cloud
    ├── Supabase Auth — учётная запись и сессия
    └── PostgreSQL — данные, RLS, ограничения и функция перехода статуса
```

Отдельного Node.js backend нет. Браузер обращается к Supabase SDK. PostgreSQL применяет RLS к запросам с учётом удостоверенной личности пользователя и отвечает за целостность данных и переходы статусов.

## Компоненты и ответственность

### Frontend

- Экраны авторизации, списка объектов, карточки объекта, карточки задачи и «Мои задачи».
- Отображение данных, полученных через SDK, и действий, доступных по роли и статусу.
- Вызов операции перехода статуса с нужными параметрами, например комментарием при возврате на доработку.
- Обработка ошибок доступа и ошибок бизнес-ограничений, возвращённых Supabase.

Frontend не считается границей безопасности: скрытие кнопки или маршрута не заменяет проверку в базе.

#### Компоновка экранов

Авторизованная часть использует минимальную навигацию через History API без отдельного роутера. `src/app/routes.ts` разбирает URL, `src/app/navigation.ts` синхронизирует React с `pushState`, `replaceState` и `popstate`. Домашний экран постановщика — `/objects`, исполнителя — `/my-tasks`. `getPathForRole` проверяет не только корень, но и сохранённые/прямые URL: исполнитель не открывает страницы объектов, а прежние ссылки `/objects/:objectId/tasks/:taskId` переводятся в `/my-tasks/:taskId`. При успешном выходе профиль и URL сбрасываются, чтобы следующему пользователю не достался маршрут предыдущей роли. Маршруты: `/objects`, `/objects/:objectId`, `/objects/:objectId/tasks/:taskId`, `/my-tasks`, `/my-tasks/:taskId`. Прямой URL сохраняется при авторизации; данные загружаются существующими RLS-защищёнными запросами. Сервер разработки и Nginx используют SPA fallback.

В DOM отображается только текущий экран. Формы объекта и задачи открываются в контентной области со своей ссылкой возврата, без действий просмотра; их несохранённые данные не кодируются в URL и теряются при обновлении. Общая белая шапка закреплена через `position: sticky; top: 0` и вынесена в `AppHeader`. На десктопе она показывает название приложения, профиль, роль и выход. До 640 px шапка занимает 59 px с границей и показывает название и кнопку с инициалами; полное имя, роль и существующий выход доступны в выпадающем меню. Меню закрывается по нажатию снаружи, Escape и переходу к десктопной ширине; Escape возвращает фокус на аватар. Родительские контейнеры не создают отдельную область прокрутки. Контент расположен под шапкой, без вертикального центрирования; сам экран авторизации сохраняет прежнюю компоновку. Список объектов использует широкую таблицу и мобильные карточки до 760 px. Просмотр объекта использует ту же широкую область: ссылка к списку, название с адресом и действия постановщика без внешней карточки. Раздел «Задачи» показывает количество и кнопку создания для постановщика, таблицу на десктопе и карточки до 760 px. Каждая строка или карточка — целиком нативная ссылка на задачу, поддерживающая Enter и обычное открытие в новой вкладке; обычный клик использует существующую SPA-навигацию. Названия и цвета статусов берутся из общего `TaskStatusBadge`. Страница задачи использует такую же широкую одноколоночную компоновку: SVG-ссылка к объекту, название и исполнитель, действия постановщика рядом с заголовком, статус с кнопкой истории и описание в отдельной белой области. Сведения об авторе и дате создания сохранены.

Общие компоненты находятся в `src/components`: `DataTable` отвечает за заголовки, контейнер, строки-ссылки, разделители, hover/focus и мобильные карточки обоих списков. Списки передают данные, заголовки, ширины колонок, адрес перехода и `renderRow`; содержимое и размещение полей на мобильном экране задаются в CSS Modules конкретного списка. Загрузка и ошибки остаются в feature-компонентах. `EmptyState` принимает заголовок, описание, иконку и необязательное действие и отображается внутри контейнера таблицы. Пустой список задач показывает одну кнопку создания только постановщику, скрывая её из заголовка. Общий `Button` используется для одинаковых кнопок создания; статусы по-прежнему используют `TaskStatusBadge`. SVG-иконки не требуют внешней библиотеки.

История и возврат на доработку используют общий `Modal` на нативном `<dialog>` с порталом в `document.body`, ограничением Tab-навигации, возвратом фокуса, Escape и блокировкой фоновой прокрутки. История показывается в хронологическом порядке: от создания задачи к последнему событию и прокручивается внутри окна. Возврат требует комментарий через общие `FormField` и `TextArea`; пустое значение проверяет прежняя клиентская функция и существующая SQL RPC. Во время запроса отправка и закрытие окна блокируются, при ошибке текст сохраняется, после успеха обновляются задача и история. `TaskActions` остаётся в потоке, использует `position: sticky; bottom: 0` на длинной странице, резервирует своё место в документе и учитывает `safe-area-inset-bottom`. При отсутствии действий контейнер не создаётся. Маршруты задачи из объекта и «Моих задач» сохранены; постановщик возвращается к объекту, исполнитель — на `/my-tasks` через параметры существующего `TaskDetails`.

Формы создания и редактирования используют отдельные `ObjectForm` и `TaskForm`. Они собираются из общих компонентов в `src/components/forms`: `FormPage`, `FormField`, `TextInput`, `TextArea`, `Select`, `FormActions`. `FormPage` имеет максимальную ширину 760 px, выравнивается слева и показывает SVG-ссылку возврата, заголовок 30 px и одну белую область формы без вложенной рамки и разделителей. Контролы используют общие стили, focus/disabled-состояния и CSS-токены; ошибки связаны с полями через `aria-describedby`. Общий `Button` поддерживает основной и нейтральный варианты. Состояние, валидация, API-запросы и результаты сохранения остаются в прежних feature-компонентах; ссылка назад выполняет тот же возврат, что и отмена, и блокируется во время сохранения.

Общие цвета, типографика, стандартные отступы, скругления, тень и длительность переходов определены в `src/styles/tokens.css`, подключённом один раз из `src/main.tsx`. CSS Modules используют семантические переменные с прежними значениями; локальные размеры и брейкпоинты остаются в стилях компонентов. Обычная строка списка объектов имеет минимальную высоту 80 px; нулевые счётчики отображаются приглушённым текстом без цветного фона.

Анимация затрагивает только область содержимого: View Transitions API, горизонтальное движение за 240 мс, обратное направление при возврате на родительский уровень и при движении назад по истории. Шапка находится вне анимируемой области и использует отдельный слой `app-header` без анимации, расположенный выше снимков содержимого. При отсутствии API или при `prefers-reduced-motion` переключение происходит без анимации.

Заголовок карточки задачи и имя постановщика берутся из выбранной задачи, включая связанный профиль автора. Список «Мои задачи» выбирает все нелогически удалённые назначенные задачи по ID профиля исполнителя существующим `listMyTasks`, а RLS ограничивает строки независимо от клиентского фильтра. `groupMyTasks` использует прежнюю группировку по объектам и разделяет четыре активных статуса и `accepted`. Основной список показывает количество активных задач и объектов, заголовки групп — название, адрес и количество задач. Названия объектов не являются ссылками. Строки используют общий `DataTable` и `/my-tasks/:taskId`, статусы — `TaskStatusBadge`. Принятые задачи раскрываются обычным React-состоянием отдельным списком; при их отсутствии кнопки нет. `EmptyState` активного списка не скрывает доступ к принятым задачам. Списки и карточки получают данные через Supabase SDK. Счётчики списка объектов сохраняют прежний расчёт: открытые задачи включают `in_review`, выполненные соответствуют `accepted`.

### Supabase Auth

- Аутентификация по email и паролю, выдача пользовательской сессии и JWT.
- Открытая регистрация выключена; тестовые пользователей создают вручную.
- Идентификатор пользователя Supabase Auth служит связью с профилем.

### PostgreSQL

- Хранит профили, объекты, задачи и историю статусов.
- Применяет RLS для ограничения доступа к строкам и проверяет разрешённые операции.
- Проверяет целостность ссылок и допустимость операций.
- Предоставляет контролируемые SQL RPC-операции для создания задачи и перехода статуса с атомарной записью истории.

## Предлагаемая модель данных

Поля ниже — предложение для реализации; точный SQL и дополнительные служебные поля будут определены миграциями.

### `profiles`

- `id` — первичный ключ и внешний ключ на `auth.users.id`.
- `role` — одна из ролей: постановщик или исполнитель.
- При необходимости: отображаемое имя и временные метки.

Связь по `id` позволяет получить профиль для удостоверенного Supabase пользователя. Все пользователи Supabase Auth обращаются к базе с PostgreSQL-ролью `authenticated`; роль приложения (постановщик или исполнитель) определяется по данным `profiles`, а не отдельными PostgreSQL-ролями.

Клиентским ролям запрещены `INSERT`, `UPDATE` и `DELETE` таблицы `profiles`. Профили и роли создаются и изменяются только административно через доверенный доступ к Supabase. Постановщик читает все профили; исполнитель — свой профиль и профили авторов и участников истории активных назначенных ему задач. RLS ограничивает доступ к строкам и не обеспечивает защиту отдельных колонок, поэтому запрет клиентского изменения роли задаётся запретом клиентской записи в таблицу целиком.

### `objects`

- Идентификатор.
- Название.
- Адрес.
- `deleted_at` — время логического удаления; `NULL` для активной записи.
- Временные метки при необходимости.

### `tasks`

- Идентификатор.
- Название и описание.
- Ссылка на объект.
- Ссылка на профиль назначенного исполнителя.
- Статус.
- Ссылка на профиль автора.
- Дата создания.
- `deleted_at` — время логического удаления; `NULL` для активной записи.

Начальный статус новой задачи — «Новая». Задача может быть создана только постановщиком.

### `task_status_history`

- Идентификатор.
- Ссылка на задачу.
- Пользователь, изменивший статус.
- Время изменения.
- Предыдущий и новый статус.
- Комментарий, допускающий отсутствие значения.

История предназначена для аудита переходов статуса и не редактируется пользователями через клиентский API.

## RLS и защита данных

RLS включается для всех пользовательских таблиц. Политики опираются на `auth.uid()` и роль связанного профиля.

- Постановщик может читать все объекты и задачи; создание, изменение и удаление объектов и задач ограничены постановщиком.
- Исполнитель может читать назначенные ему задачи и объекты, связанные с его задачами. Он не получает доступа к задачам других исполнителей.
- Исполнитель может читать профиль только самого себя, автора или участника истории активной задачи, назначенной ему. Политика профилей опирается на RLS-защищённые строки задач и истории и не раскрывает посторонние профили.
- Исполнитель не имеет права напрямую редактировать поля задачи. Его действия по задачам выполняются только через разрешённые переходы статуса.
- Постановщик может редактировать разрешённые поля задачи, но не поле `status`; необходимые гранты на изменение колонок задаются отдельно от RLS.
- История доступна только для чтения авторизованным пользователям, имеющим право просматривать соответствующую задачу. Прямые `INSERT`, `UPDATE` и `DELETE` через клиентский API запрещены.
- Для клиентского API физический `DELETE` объектов и задач запрещён. Логическое удаление через установку `deleted_at` доступно только постановщику. Активные списки и операции исключают записи с `deleted_at IS NOT NULL`; историю задач не удаляют.
- Удалённая задача не может менять статус. Логическое удаление объекта атомарно устанавливает `deleted_at` и для всех его активных задач; история задач сохраняется.

Текущие гранты разрешают постановщику менять у активной задачи только `title`, `description` и `assignee_id`, независимо от статуса; `status`, `object_id`, `author_id` и `deleted_at` напрямую не обновляются. Ограничения редактирования по статусам остаются открытым бизнес-вопросом и в текущей схеме отдельно не кодируются.

Конкретные `USING`/`WITH CHECK` выражения и гранты на таблицы и колонки должны быть определены миграциями, а доступ к таблицам проверен прямыми запросами с пользовательскими JWT.

`service_role` остаётся административной ролью Supabase с её штатными привилегиями; прикладные ограничения доступа не должны искусственно урезать её возможности. Браузерное приложение использует только `authenticated`, а секретный ключ `service_role` нельзя помещать во frontend.

## Переходы статусов

Все переходы статуса выполняются только SQL RPC-функцией `transition_task_status(task_id, new_status, comment)`, определённой с `SECURITY DEFINER`: клиентские роли не имеют прямых прав на изменение `tasks.status` и запись в `task_status_history`. Функция работает с `SET search_path = ''` и использует полную квалификацию имён таблиц и других объектов БД. Прямой клиентский `UPDATE` колонки `tasks.status` запрещён. Функция выполняет в одной транзакции следующие шаги:

1. Определяет пользователя по `auth.uid()` и загружает его профиль и роль.
2. Блокирует строку целевой задачи (`SELECT ... FOR UPDATE`), чтобы сериализовать конкурентные переходы, и проверяет её текущий статус. Логически удалённая задача не может менять статус.
3. Проверяет назначение, роль и допустимость конкретного перехода:
   - постановщик: «На проверке» → «Принята»;
   - постановщик: «На проверке» → «На доработке» при непустом комментарии;
   - назначенный исполнитель: «Новая» → «В работе»;
   - назначенный исполнитель: «В работе» → «На проверке»;
   - назначенный исполнитель: «На доработке» → «В работе».
4. Обновляет статус задачи и добавляет запись истории с `auth.uid()`, временем, старым и новым статусом и комментарием.
5. При любой ошибке откатывает обе записи.

Функция обязательно проверяет `auth.uid()`, наличие профиля, роль пользователя, его полномочия и назначение задачи; полномочия проверяются по данным приложения, а не через отдельные PostgreSQL-роли для постановщиков и исполнителей. Право `EXECUTE` отзывается у `PUBLIC` и `anon` и предоставляется `authenticated`. Функции выдаются только минимальные привилегии, необходимые для проверенного перехода. Прямое изменение статуса недоступно клиентам на уровне грантов, а история записывается функцией в той же транзакции без прямых клиентских прав записи.

Создание задачи постановщиком выполняется отдельной SQL RPC-функцией с `SECURITY DEFINER`, поскольку клиентские роли не имеют прямого права записи в `task_status_history`. Функция работает с `SET search_path = ''`, использует полную квалификацию имён объектов БД, проверяет `auth.uid()`, наличие профиля, роль постановщика и его полномочие создавать задачу. Право `EXECUTE` отзывается у `PUBLIC` и `anon` и предоставляется `authenticated`; функции выдаются только минимальные необходимые привилегии. В одной транзакции функция создаёт задачу со статусом «Новая» и начальную запись истории «— → Новая» с автором `auth.uid()`. Клиент не получает прямого права добавлять события истории.

Публичные привилегированные функции принадлежат отдельной роли БД `crm_rpc_owner` с атрибутом `NOLOGIN` и ограниченными явными грантами на нужные таблицы и колонки. Этой роли нужен `BYPASSRLS`, поскольку защищённые операции выполняются вне клиентских политик; она не получает права создавать объекты схемы после передачи ей функций. Вспомогательная `private.current_user_id()` вызывает `auth.uid()` и возвращает только идентификатор текущего пользователя; исполнять её может только `crm_rpc_owner`. `crm_rpc_owner` — только владелец SQL-функций, не роль пользователя приложения: постановщик и исполнитель по-прежнему определяются данными `profiles`.

## Поток авторизации

1. Пользователь вводит email и пароль на экране авторизации.
2. Frontend передаёт учётные данные Supabase Auth через SDK.
3. После успешной аутентификации SDK хранит сессию и прикладывает JWT к запросам.
4. PostgreSQL извлекает `auth.uid()` из JWT, связывает его с `profiles` и применяет RLS.
5. Интерфейс загружает доступный профиль и строит представление с учётом роли; база повторно проверяет каждую операцию.
6. Выход завершает пользовательскую сессию через SDK.

## Работа с данными

- Список объектов и задачи объекта загружаются через SDK; ответ ограничивается RLS.
- «Мои задачи» запрашивает задачи текущего исполнителя. Политики БД остаются обязательным ограничителем даже при некорректном фильтре клиента.
- Карточка задачи загружает данные и историю только для доступной пользователю задачи.
- Постановщик редактирует разрешённые поля, кроме статуса, и логически удаляет объекты и задачи установкой `deleted_at`; физическое удаление через клиентский API запрещено.
- Исполнитель не редактирует поля задач напрямую; смена статуса доступна назначенному исполнителю только через `transition_task_status`.
- Смена статуса всегда выполняется через SQL-функцию; клиент не обновляет статус напрямую.
- Ошибки авторизации, доступа, неверного перехода и проверки обязательного комментария показываются пользователю понятным сообщением.
